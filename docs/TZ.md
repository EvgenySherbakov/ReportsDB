# ТЗ: локальная база данных отчётности SSRS + аналитика

> Документ является **источником истины** для проекта. Любой AI-агент, продолжающий
> работу, обязан прочитать его целиком перед первым изменением кода и обновить
> раздел [15. Журнал решений](#15-журнал-решений) после внесения изменений.

---

## 1. Контекст и цель

В организации эксплуатируется набор отчётов SSRS (SQL Server Reporting Services).
Информация о них живёт в Excel-файле и не поддаётся анализу: нельзя ответить на
вопросы «какие отчёты можно вывести из эксплуатации», «какие таблицы критичны»,
«сколько данных обслуживает каждый отчёт».

**Цель:** превратить Excel-выгрузку в локальную реляционную БД с готовой
аналитикой, которую можно передать коллеге одним файлом/архивом и запустить без
администраторских прав и без сервера.

**Не является целью:** замена SSRS, онлайн-мониторинг, многопользовательская
работа, запись данных пользователями.

## 2. Ключевые решения (зафиксированы с заказчиком)

| Вопрос | Решение | Обоснование |
| --- | --- | --- |
| СУБД | **DuckDB** (файл `data/reports.duckdb`) | Встраиваемая, один файл, нулевая установка, колоночная — идеальна для аналитических агрегатов. SQL-диалект близок к PostgreSQL. |
| Визуализация, вариант A | **Streamlit + Plotly** | Полноценное интерактивное приложение, произвольный SQL, фильтры. Для коллег с Docker или Python. |
| Визуализация, вариант B | **Самодостаточный HTML-файл** | Для коллег, у которых нет ничего кроме браузера. Передаётся по почте, открывается двойным кликом. |
| Доставка коллегам | Docker-образ **или** один HTML-файл | Заказчик подтвердил: на машинах доступны Docker и браузер. Python не гарантирован. |
| Режим загрузки данных | **Разовая полная пересборка** (`full refresh`) | Историчность не требуется. ETL идемпотентен: повторный запуск пересоздаёт БД с нуля. |
| Приоритет аналитики | **Объём данных и стоимость** | Главный сценарий — сколько данных обслуживает каждый отчёт и что это стоит. |

### 2.1. Осознанное отклонение по варианту B

Изначально обсуждался DuckDB-WASM внутри HTML. **Реализовано иначе:** данные
встраиваются в HTML как JSON, агрегация выполняется на чистом JavaScript.

Причина: DuckDB-WASM при открытии страницы по протоколу `file://` требует
загрузки `.wasm` и worker-скрипта, что блокируется политикой CORS браузера;
обход через инлайн base64 раздувает файл до десятков мегабайт и остаётся
хрупким. Объём данных (сотни отчётов, тысячи таблиц) на порядки меньше порога,
где нужен движок БД. Требование заказчика — «открывается двойным кликом, ничего
ставить не надо» — выполняется полностью и надёжнее.

Если в будущем HTML будет раздаваться по HTTP, переход на DuckDB-WASM возможен
без изменения модели данных.

## 3. Исходные данные

### 3.1. Файл, доступный сейчас

Excel-файл (`.xls`/`.xlsx`) со строкой на отчёт. **Фактические заголовки
подтверждены заказчиком:**

| Заголовок в файле | Поле модели | Пример значения |
| --- | --- | --- |
| `№` | `report_no` | `17` |
| `Наименование отчета` | `report_name` | `Sales Monthly Summary` |
| `Каталог` | `catalog_path` | `/Finance/Monthly/Sales` |
| `Таблицы источники данных` | `source_tables` | `dbo.Orders;dbo.Customers;sales.Invoice` |

Список таблиц лежит **в одной ячейке**, элементы в формате `схема.таблица`,
разделитель `;`.

Колонка `№` сохраняется в `dim_report.report_no` как **текст** (встречаются
значения вида `1.2`) и выводится в приложении и в HTML — чтобы находить отчёт в
оригинальной таблице. Заголовок `Наименование отчета` написан без «ё»;
сопоставление приводит `ё` к `е`, поэтому оба написания работают.

### 3.1.1. Данные не покидают машину

Заказчик работает с рабочими данными, **исходные файлы и собранная БД в
репозиторий не попадают**. Обеспечено `.gitignore`: `data/raw/*`,
`data/*.duckdb`, `dist/`. В git лежит только код, SQL и конфиг с именами
колонок. Проверяется тестом `test_raw_data_is_git_ignored`.

Отсюда следствия, которые обязан соблюдать любой агент:

- никогда не коммитить содержимое `data/` и `dist/`;
- не вставлять реальные имена отчётов, таблиц и схем в код, тесты, README,
  сообщения коммитов и описания PR;
- для примеров использовать только синтетику из `python -m reportsdb sample`;
- Docker-образ содержит `data/` — он предназначен для передачи внутри команды
  и не должен публиковаться в открытых реестрах.

### 3.2. Данные, которые появятся позже

1. **Размеры таблиц в БД** — строк, МБ данных, МБ индексов.
2. **Частота использования отчётов** — число запусков за период, число
   пользователей, средняя длительность.

Схема БД и ETL **уже рассчитаны** на эти данные: таблицы `fact_table_size` и
`fact_report_usage` создаются всегда, при отсутствии файлов остаются пустыми, а
витрины корректно отдают `NULL` вместо падения.

### 3.3. Правило: никаких предположений о колонках

Имена колонок в Excel заранее неизвестны и могут быть на русском. Поэтому:

- Соответствие «колонка файла → поле модели» задаётся **только** в
  `config/mapping.yml`.
- Перед первой загрузкой агент обязан выполнить `reportsdb profile <файл>`,
  посмотреть реальные заголовки и заполнить маппинг.
- **Запрещено** хардкодить имена колонок в коде ETL.
- Сопоставление ведётся без учёта регистра и краевых пробелов; поддерживается
  список синонимов на поле.

## 4. Модель данных

Схема «звезда» с мостом для связи многие-ко-многим.

```
        dim_report ──< bridge_report_table >── dim_table
             │                                     │
             │                                     │
      fact_report_usage                     fact_table_size
```

### 4.1. `dim_report` — отчёты

| Поле | Тип | Описание |
| --- | --- | --- |
| `report_id` | `INTEGER PK` | Суррогатный ключ |
| `report_no` | `VARCHAR` | Номер из колонки «№» исходного файла; текстом |
| `report_name` | `VARCHAR NOT NULL` | Имя отчёта |
| `catalog_path` | `VARCHAR` | Полный путь в каталоге SSRS, нормализованный |
| `folder_l1`…`folder_l3` | `VARCHAR` | Первые три уровня папок — для группировок |
| `folder_depth` | `INTEGER` | Глубина вложенности |
| `description` | `VARCHAR` | Опционально |
| `owner` | `VARCHAR` | Опционально |
| `source_row` | `INTEGER` | Номер строки в исходном файле — для трассировки |

`UNIQUE (catalog_path, report_name)`.

### 4.2. `dim_table` — таблицы-источники

| Поле | Тип | Описание |
| --- | --- | --- |
| `table_id` | `INTEGER PK` | Суррогатный ключ |
| `schema_name` | `VARCHAR NOT NULL` | Схема; если в исходнике не указана — `(unknown)` |
| `table_name` | `VARCHAR NOT NULL` | Имя таблицы |
| `full_name` | `VARCHAR NOT NULL UNIQUE` | `schema_name.table_name`, нижний регистр |
| `is_parsed_ok` | `BOOLEAN` | `FALSE`, если строку не удалось разобрать |

Нормализация: обрезка пробелов, снятие квадратных скобок `[dbo].[Orders]` →
`dbo.Orders`, приведение к нижнему регистру для ключа сопоставления.
Отображаемое имя сохраняется как есть.

### 4.3. `bridge_report_table` — мост

| Поле | Тип |
| --- | --- |
| `report_id` | `INTEGER` |
| `table_id` | `INTEGER` |

`PRIMARY KEY (report_id, table_id)` — дубликаты внутри одной ячейки схлопываются.

### 4.4. `fact_table_size` — размеры (заполняется позже)

| Поле | Тип | Описание |
| --- | --- | --- |
| `table_id` | `INTEGER PK` | |
| `row_count` | `BIGINT` | Число строк |
| `data_mb` | `DOUBLE` | Данные, МБ |
| `index_mb` | `DOUBLE` | Индексы, МБ |
| `total_mb` | `DOUBLE` | Итого; если не задано — `data_mb + index_mb` |
| `measured_at` | `DATE` | Дата замера |

### 4.5. `fact_report_usage` — использование (заполняется позже)

| Поле | Тип | Описание |
| --- | --- | --- |
| `report_id` | `INTEGER PK` | |
| `exec_count` | `BIGINT` | Запусков за период |
| `distinct_users` | `INTEGER` | Уникальных пользователей |
| `avg_duration_ms` | `DOUBLE` | Средняя длительность |
| `last_executed_at` | `DATE` | Последний запуск |
| `period_start`, `period_end` | `DATE` | Границы периода |

### 4.6. `etl_run` и `etl_reject` — служебные

`etl_run` фиксирует время загрузки, имя исходного файла, его SHA-256, число
строк и версию кода. `etl_reject` хранит строки, которые не удалось разобрать,
с причиной — молчаливая потеря данных недопустима.

## 5. Витрины (SQL-представления)

Создаются в `sql/02_views.sql`. Все обязаны корректно работать при пустых
`fact_table_size` / `fact_report_usage`.

### 5.1. `v_report_footprint` — объём данных на отчёт ⭐ приоритет

Для каждого отчёта:

- `table_count` — число таблиц-источников;
- `gross_mb` — сумма `total_mb` всех его таблиц;
- `exclusive_mb` — сумма `total_mb` **только тех таблиц, которые не использует ни один другой отчёт**;
- `shared_mb` = `gross_mb − exclusive_mb`;
- `gross_rows`, `exclusive_rows` — то же по числу строк;
- `size_coverage_pct` — доля таблиц отчёта, для которых известен размер.

> **Критично.** `gross_mb` при суммировании по всем отчётам многократно
> учитывает общие таблицы и **не является** объёмом хранилища. Реальная выгода
> от вывода отчёта из эксплуатации — это `exclusive_mb`. Оба показателя
> обязаны присутствовать, а в UI рядом с `gross_mb` должно стоять пояснение.
> `size_coverage_pct` защищает от вывода по неполным данным.

### 5.2. `v_table_criticality` — критичность таблиц

`full_name`, `report_count` (сколько отчётов зависит), `total_mb`, `row_count`,
`is_orphan` (`report_count = 0`), список отчётов.

### 5.3. `v_report_cost_value` — стоимость против ценности

Соединяет footprint и usage. Поля: `exclusive_mb`, `exec_count`,
`mb_per_execution`, и `quadrant` ∈ {`Дорогой и невостребованный`,
`Дорогой и востребованный`, `Дешёвый и невостребованный`,
`Дешёвый и востребованный`, `Нет данных об использовании`}.
Границы квадрантов — медианы по непустым значениям.

### 5.4. `v_decommission_candidates` — кандидаты на вывод

Отчёты, отсортированные по убыванию `exclusive_mb`, среди тех, где
`exec_count = 0` или `NULL`. Колонка `confidence` понижается, если
`size_coverage_pct < 100` или данных об использовании нет.

### 5.5. `v_catalog_overview` и `v_schema_overview`

Агрегаты по папкам каталога (`folder_l1`) и по схемам БД: число отчётов, число
таблиц, суммарный объём.

### 5.6. `v_report_overlap` — пересечение отчётов

Пары отчётов с коэффициентом Жаккара по множествам таблиц ≥ 0.8 — кандидаты на
объединение. Ограничение: только пары, где у обоих ≥ 2 таблицы.

## 7. ETL: требования к поведению

1. **Идемпотентность.** `build` всегда пересоздаёт `reports.duckdb` с нуля.
   Существующий файл переименовывается в `reports.duckdb.bak` (одна копия).
2. **Разбор списка таблиц.** Разделитель `;` (настраивается). Пустые элементы
   отбрасываются. Элемент без точки → `schema_name = '(unknown)'`,
   `is_parsed_ok = FALSE`. Элемент с двумя и более точками → берутся два
   последних сегмента (случай `db.schema.table`), остальное отбрасывается.
3. **Нормализация пути каталога.** Обратные слэши → прямые, схлопывание
   повторов, ведущий `/`, без завершающего `/`. Пустой путь → `/`.
4. **Отбраковка.** Строка без имени отчёта попадает в `etl_reject` и не
   прерывает загрузку. Строка без таблиц загружается — отчёт без источников
   валиден и интересен аналитике.
5. **Отчёт о загрузке.** В stdout: число строк прочитано / загружено /
   отброшено, число уникальных таблиц, число неразобранных элементов.
6. **Кодировка и типы.** Все текстовые поля читаются как строки — недопустимо,
   чтобы pandas превратил `1.2` в имя таблицы или потерял ведущие нули.

## 8. Streamlit-приложение (вариант A)

Страницы:

1. **Обзор** — KPI: отчётов, таблиц, связей, суммарный `exclusive_mb`, покрытие
   размерами; распределение по папкам каталога.
2. **Объём и стоимость** ⭐ — таблица `v_report_footprint` с сортировкой,
   диаграмма топ-20 по `exclusive_mb`, скаттер «объём против частоты».
3. **Таблицы** — `v_table_criticality`, поиск, переход к зависимым отчётам.
4. **Кандидаты на вывод** — `v_decommission_candidates` с фильтром по
   `confidence`, выгрузка в CSV.
5. **SQL** — произвольный запрос к БД с ограничением 5000 строк и выгрузкой CSV.

Требования: работа полностью офлайн (без CDN), кириллица в подписях,
единая палитра, все таблицы выгружаются в CSV.

## 9. Самодостаточный HTML (вариант B)

Один файл `dist/reportsdb.html`. Внутри: данные как JSON, стили и скрипты
инлайном, ноль внешних запросов. Обязан открываться по `file://` в Chrome, Edge,
Firefox.

Содержит: KPI-строку, таблицу отчётов с сортировкой/поиском/фильтром по папке,
таблицу критичности таблиц, топ кандидатов на вывод, выгрузку текущей выборки в
CSV. Поддержка светлой и тёмной темы. Целевой размер — до 5 МБ.

## 11. Порядок работы агента при появлении реального Excel-файла

0. Убедиться, что `data/raw/` под `.gitignore` (см. 3.1.1). Файл заказчика
   никуда не выкладывается.
1. Положить файл в `data/raw/`.
2. `python -m reportsdb profile data/raw/<файл>` — вывести листы, заголовки,
   по 5 примеров значений, долю пустых.
3. Заполнить `config/mapping.yml` по факту. Ничего не угадывать: если смысл
   колонки неясен — спросить заказчика.
4. `python -m reportsdb build` — собрать БД. Проверить сводку и `etl_reject`.
5. Прогнать `tests/` — контрольные проверки целостности.
6. `python -m reportsdb export-html` — собрать HTML.
7. Обновить раздел 15 и запушить.

## 12. Контроль качества

Проверки в `tests/test_integrity.py`, запускаются на синтетических данных и на
реальных:

- у каждой связи в мосте существуют обе стороны (нет висячих ключей);
- `full_name` в `dim_table` уникален;
- сумма `exclusive_mb` по всем отчётам ≤ сумме `total_mb` по всем таблицам —
  ключевая защита от двойного учёта;
- число строк исходника = загружено + отброшено;
- все витрины выполняются на пустых фактах и возвращают результат без ошибок;
- фактические заголовки заказчика (`№`, `Наименование отчета`, `Каталог`,
  `Таблицы источники данных`) сопоставляются без правок конфига;
- `.gitignore` закрывает `data/raw/*`, `data/*.duckdb` и `dist/`.

## 13. Ограничения и риски

| Риск | Смягчение |
| --- | --- |
| Список таблиц в Excel неполон или устарел (заполнялся руками) | В UI явная оговорка: анализ отражает содержимое файла, а не фактические зависимости. Достоверный источник — парсинг `.rdl` или `ReportServer.ExecutionLog`. |
| Двойной учёт общих таблиц | Введён `exclusive_mb`; `gross_mb` помечен как небезопасный для суммирования. |
| Неполные данные о размерах | `size_coverage_pct` и понижение `confidence`. |
| Отчёт может тянуть данные через хранимые процедуры и вьюхи | Фиксируется как известное ограничение; при появлении данных добавить `object_type` в `dim_table`. |
