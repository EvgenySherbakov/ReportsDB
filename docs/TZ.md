# ТЗ: локальная база данных отчётности SSRS + аналитика

**Русский** · [English](TZ.en.md)

> Документ является **источником истины** для проекта. Любой AI-агент, продолжающий
> работу, обязан прочитать его целиком перед первым изменением кода и обновить

## 1. Контекст и цель

В организации эксплуатируется набор отчётов SSRS (SQL Server Reporting Services).
Информация о них живёт в Excel-файле и не поддаётся анализу: нельзя ответить на
вопросы «какие отчёты можно вывести из эксплуатации», «какие таблицы критичны»,
«сколько данных обслуживает каждый отчёт».

**Цель:** превратить Excel-выгрузку в локальную реляционную БД с готовой
аналитикой, которую можно передать коллеге одним файлом/архивом и запустить без
администраторских прав и без сервера.

**Не является целью:** замена SSRS, онлайн-мониторинг, многопользовательская
работа, запись данных пользователями.

## 2. Ключевые решения (зафиксированы с заказчиком)

| Вопрос | Решение | Обоснование |
| --- | --- | --- |
| СУБД | **DuckDB** (файл `data/reports.duckdb`) | Встраиваемая, один файл, нулевая установка, колоночная — идеальна для аналитических агрегатов. SQL-диалект близок к PostgreSQL. |
| Визуализация, вариант A | **Streamlit + Plotly** | Полноценное интерактивное приложение, произвольный SQL, фильтры. Для коллег с Docker или Python. |
| Визуализация, вариант B | **Самодостаточный HTML-файл** | Для коллег, у которых нет ничего кроме браузера. Передаётся по почте, открывается двойным кликом. |
| Доставка коллегам | Docker-образ **или** один HTML-файл | Заказчик подтвердил: на машинах доступны Docker и браузер. Python не гарантирован. |
| Режим загрузки данных | **Разовая полная пересборка** (`full refresh`) | Историчность не требуется. ETL идемпотентен: повторный запуск пересоздаёт БД с нуля. |
| Приоритет аналитики | **Объём данных и стоимость** | Главный сценарий — сколько данных обслуживает каждый отчёт и что это стоит. |

### 2.1. Осознанное отклонение по варианту B

Изначально обсуждался DuckDB-WASM внутри HTML. **Реализовано иначе:** данные
встраиваются в HTML как JSON, агрегация выполняется на чистом JavaScript.

Причина: DuckDB-WASM при открытии страницы по протоколу `file://` требует
загрузки `.wasm` и worker-скрипта, что блокируется политикой CORS браузера;
обход через инлайн base64 раздувает файл до десятков мегабайт и остаётся
хрупким. Объём данных (сотни отчётов, тысячи таблиц) на порядки меньше порога,
где нужен движок БД. Требование заказчика — «открывается двойным кликом, ничего
ставить не надо» — выполняется полностью и надёжнее.

Если в будущем HTML будет раздаваться по HTTP, переход на DuckDB-WASM возможен
без изменения модели данных.

## 3. Исходные данные

### 3.1. Файл, доступный сейчас

Excel-файл (`.xls`/`.xlsx`) со строкой на отчёт. **Фактические заголовки
подтверждены заказчиком:**

| Заголовок в файле | Поле модели | Смысл |
| --- | --- | --- |
| `№` | `report_no` | Номер строки в исходной таблице |
| `ТС` | `network` | Торговая сеть |
| `Завод` | `plant` | Завод внутри сети |
| `Каталог 1-го уровня` | `folder_l1` | Путь пользователя к отчёту, уровень 1 |
| `Каталог 2-го уровня` | `folder_l2` | Уровень 2 |
| `Каталог 3-го уровня` | `folder_l3` | Уровень 3 |
| `Наименование отчета` | `report_name` | Имя отчёта (обязательное поле) |
| `Используется view` | `uses_view` | Обращается ли отчёт к данным через view |
| `Таблицы источники данных` | `source_tables` | Список таблиц через `;` |
| `View` | `source_views` | Список view через `;` |
| `Mat.view` | `source_matviews` | Список материализованных view |
| `Временные таблицы` | `source_temp_tables` | Временные и generated-объекты |
| `Функции/процедуры` | `source_routines` | Список функций и процедур |
| `Ср. дл. (сек)` | `avg_duration_sec` | Средняя длительность выборки, секунды |
| `Кол-во обращений` | `exec_count` | Сколько раз отчёт запускался |

Правила разбора:

- Список таблиц лежит **в одной ячейке**, элементы в формате `схема.таблица`,
  разделитель `;`.
- `catalog_path` **собирается** из трёх колонок уровней: пустые уровни
  пропускаются, слэш внутри значения заменяется на дефис. Одна колонка
  «Каталог» поддерживается как запасной вариант для файлов старой структуры.
- Ключ уникальности отчёта — `(network, plant, catalog_path, report_name)`:
  один и тот же отчёт существует для разных сетей и заводов, схлопывать такие
  строки нельзя.
- `report_no` хранится **текстом** (встречаются значения вида `1.2`).
- `uses_view` разбирается терпимо: `да/нет`, `yes/no`, `1/0`, `+/-`.
  Непонятное значение даёт `NULL`, а не `FALSE` — «неизвестно» и «нет» ведут к
  разным выводам.
- `Наименование отчета` написано без «ё»; сопоставление приводит `ё` к `е`,
  поэтому оба написания работают.

**Тип объекта определяется колонкой, из которой объект пришёл** — это надёжнее
догадок по имени: таблица `V_SALES` останется таблицей, если лежит в колонке
таблиц. В `dim_table.kind_source` записывается, откуда тип известен:
«колонка», «маска» или «по умолчанию».

Маски имён (`reports.object_patterns` в `mapping.yml`) — **последняя догадка**,
и работают они только для колонки «Таблицы источники данных». По умолчанию
включена ровно одна: `VIEW: ["V_*", "VW_*"]`. Список закреплён тестом, потому
что неверно угаданный тип молча выкинул бы таблицу из таблицы №2 и из расчёта
объёма — новая маска добавляется осознанно, а не мимоходом.

**Маска не применяется к объектам, найденным в файле размеров.** Наличие
сегментов означает, что объект физически хранится, — это таблица, как бы она ни
называлась. Для этого перед разбором отчётов по файлу размеров строится не
только индекс схем (см. 7.2.1), но и множество всех его имён.

**Статистика использования приходит в основном файле.** Колонки
`Кол-во обращений` и `Ср. дл. (сек)` загружаются прямо в `fact_report_usage`.
Отдельный файл статистики остаётся поддержан и **перекрывает** эти значения:
он считается более свежим источником и может нести поля, которых нет в
основном файле (пользователи, границы периода).

### 3.1.1. Данные не покидают машину

Заказчик работает с рабочими данными, **исходные файлы и собранная БД в
репозиторий не попадают**. Обеспечено `.gitignore`: `data/raw/*`,
`data/*.duckdb`, `dist/`. В git лежит только код, SQL и конфиг с именами
колонок. Проверяется тестом `test_raw_data_is_git_ignored`.

Отсюда следствия, которые обязан соблюдать любой агент:

- никогда не коммитить содержимое `data/` и `dist/`;
- не вставлять реальные имена отчётов, таблиц и схем в код, тесты, README,
  сообщения коммитов и описания PR;
- для примеров использовать только синтетику из `python -m reportsdb sample`;
- Docker-образ содержит `data/` — он предназначен для передачи внутри команды
  и не должен публиковаться в открытых реестрах.

### 3.2. Файл размеров — выгрузка сегментов БД

Второй файл: строка на **сегмент**, а не на таблицу.

| Заголовок | Поле модели | Смысл |
| --- | --- | --- |
| `№` | — | Порядковый номер, не используется |
| `ТС` | `network` | Торговая сеть. Необязательна |
| `Завод` | `plant` | Завод. Необязателен |
| `OWNER` | `schema_name` | Схема |
| `SEGMENT_NAME` | `table_name` | Имя сегмента |
| `SEGMENT_TYPE` | `segment_type` | `TABLE`, `TABLE PARTITION`, `INDEX`, … |
| `SIZE_MB` | `total_mb` | Размер сегмента, МБ |
| `PERCENT_OF_TOTAL` | `percent_of_total` | Доля в общем объёме БД, % |
| `Глубина хранения` | `retention_days` | Сколько дней данных хранит таблица |
| `PERCENT_OF_SCHEMA` | — | Доля в схеме, не используется |

Четыре правила, без которых цифры будут неверными:

1. **Сегменты одной таблицы суммируются.** У секционированной таблицы
   несколько строк выгрузки; `SIZE_MB` и `PERCENT_OF_TOTAL` складываются,
   число сложенных строк пишется в `segment_count`.
2. **Учитываются только сегменты типа `TABLE*`.** Список задан в
   `mapping.yml` (`table_sizes.segment_types`). Индексные и LOB-сегменты
   носят собственные имена, привязать их к таблице по этой выгрузке нельзя —
   поэтому размер индексов в объём таблицы **не входит**. Число пропущенных
   сегментов выводится в сводке загрузки.
3. **Размер ведётся по заводам.** Одна и та же таблица на разных заводах
   занимает разное место, поэтому сегменты складываются в разрезе
   `(таблица, ТС, завод)`. Если колонок `ТС` и `Завод` в файле нет, строки
   попадают в «(не указана)» / «(не указан)» и применяются ко всем отчётам.
4. **Файл размеров — единственный источник списка таблиц БД.** Загружаются
   **все** его строки, а не только таблицы из отчётов: таблица, которой нет ни
   в одном отчёте, заводится в `dim_table` с `kind_source = 'файл размеров'` и
   попадает в каталог `v_tables_catalog`. Обратное неверно: объект, который
   упомянут в отчёте, но отсутствует в файле размеров, в каталог **не
   добавляется** — мост «отчёт ↔ таблица» лишь ссылается на этот список.
   Число таблиц, встретившихся только в файле размеров, выводится в сводке
   загрузки; сколько ссылок отчётов повисло без размера, видно в
   `size_coverage_pct` и подписью под таблицей №1.

### 3.2.1. Что появится позже

Число строк по таблицам (`row_count`) и границы периода статистики. Поля в
модели есть, при отсутствии данных остаются пустыми — витрины к этому готовы.

### 3.3. Правило: никаких предположений о колонках

Имена колонок в Excel заранее неизвестны и могут быть на русском. Поэтому:

- Соответствие «колонка файла → поле модели» задаётся **только** в
  `config/mapping.yml`.
- Перед первой загрузкой агент обязан выполнить `reportsdb profile <файл>`,
  посмотреть реальные заголовки и заполнить маппинг.
- **Запрещено** хардкодить имена колонок в коде ETL.
- Сопоставление ведётся без учёта регистра и краевых пробелов; поддерживается
  список синонимов на поле.

## 4. Модель данных

Схема «звезда» с мостом для связи многие-ко-многим.

```
        dim_report ──< bridge_report_table >── dim_table
             │                                     │
             │                                     │
      fact_report_usage                     fact_table_size
```

### 4.1. `dim_report` — отчёты

| Поле | Тип | Описание |
| --- | --- | --- |
| `report_id` | `INTEGER PK` | Суррогатный ключ |
| `report_no` | `VARCHAR` | Номер из колонки «№» исходного файла; текстом |
| `report_name` | `VARCHAR NOT NULL` | Имя отчёта |
| `network` | `VARCHAR` | Торговая сеть |
| `plant` | `VARCHAR` | Завод |
| `uses_view` | `BOOLEAN` | Отчёт обращается к данным через view |
| `catalog_path` | `VARCHAR` | Путь, собранный из трёх колонок уровней |
| `folder_l1`…`folder_l3` | `VARCHAR` | Первые три уровня папок — для группировок |
| `folder_depth` | `INTEGER` | Глубина вложенности |
| `description` | `VARCHAR` | Опционально |
| `owner` | `VARCHAR` | Опционально |
| `source_row` | `INTEGER` | Номер строки в исходном файле — для трассировки |

`UNIQUE (network, plant, catalog_path, report_name)`.

### 4.2. `dim_table` — таблицы-источники

| Поле | Тип | Описание |
| --- | --- | --- |

`etl_run` фиксирует время загрузки, имя исходного файла, его SHA-256, число
строк и версию кода. `etl_reject` хранит строки, которые не удалось разобрать,
с причиной — молчаливая потеря данных недопустима.

## 5. Витрины (SQL-представления)

Создаются в `sql/02_views.sql`. Все обязаны корректно работать при пустых
`fact_table_size` / `fact_report_usage`.

### 5.0. `v_report_table_size` — размер таблицы для конкретного отчёта

Служебная витрина, на которую опираются все остальные. Раз размер хранится по
заводам, наивное `JOIN fact_table_size USING (table_id)` размножило бы строки
отчёта в столько раз, на скольких заводах живёт его таблица, и объём вырос бы
кратно. Витрина берёт для каждой пары «отчёт + таблица» **ровно одну** строку
размера: сначала замер завода самого отчёта, при его отсутствии — общий замер
«(не указана)» / «(не указан)».

Колонки: `report_id`, `table_id`, `total_mb`, `row_count`, `retention_days`,
`percent_of_total`, `segment_count`, `has_size` (размер найден),
`size_is_plant_specific` (найден именно для завода отчёта, а не общий).

**Правило для агента:** соединять отчёт с размером только через эту витрину.
Прямой join к `fact_table_size` в новых запросах — ошибка.

### 5.1. `v_report_footprint` — объём данных на отчёт ⭐ приоритет

Для каждого отчёта:

- `table_count` — число таблиц-источников;
- `gross_mb` — сумма `total_mb` всех его таблиц;
- `exclusive_mb` — сумма `total_mb` **только тех таблиц, которые не использует ни один другой отчёт**;
- `shared_mb` = `gross_mb − exclusive_mb`;
- `gross_rows`, `exclusive_rows` — то же по числу строк;
- `size_coverage_pct` — доля таблиц отчёта, для которых известен размер;
- `exclusive_pct_of_db` — какую долю всей БД занимают эксклюзивные таблицы
  отчёта; сумма по отчётам корректна, как и у `exclusive_mb`.

> **Критично.** `gross_mb` при суммировании по всем отчётам многократно
> учитывает общие таблицы и **не является** объёмом хранилища. Реальная выгода
> от вывода отчёта из эксплуатации — это `exclusive_mb`. Оба показателя
> обязаны присутствовать, а в UI рядом с `gross_mb` должно стоять пояснение.
> `size_coverage_pct` защищает от вывода по неполным данным.

### 5.2. `v_table_criticality` — критичность таблиц

`full_name`, `report_count` (сколько отчётов зависит), `total_mb`, `row_count`,
`is_orphan` (`report_count = 0`), список отчётов.

### 5.3. `v_report_cost_value` — стоимость против ценности

Соединяет footprint и usage. Стоимость меряется **двумя независимыми
величинами**: объёмом данных (`exclusive_mb`) и временем
(`total_duration_sec` = `exec_count` × `avg_duration_sec`). Отчёт может быть
дешёвым по данным и дорогим по времени — это разные поводы для действий.

Поля: `exclusive_mb`, `exec_count`, `avg_duration_sec`, `total_duration_sec`,
`mb_per_execution`, и `quadrant` ∈ {`Дорогой и невостребованный`,
`Дорогой и востребованный`, `Дешёвый и невостребованный`,
`Дешёвый и востребованный`, `Нет данных об использовании`}.
Границы квадрантов — медианы по непустым значениям.

### 5.4. `v_decommission_candidates` — кандидаты на вывод

Отчёты, отсортированные по убыванию `exclusive_mb`, среди тех, где
`exec_count = 0` или `NULL`. Колонка `confidence` понижается, если:

- данных об использовании нет;
- **отчёт обращается к данным через view** — за view стоят таблицы, которых
  нет в списке источников, поэтому объём такого отчёта посчитан не полностью;
- `size_coverage_pct < 100` — размеры известны не по всем таблицам.

### 5.5. `v_network_overview` — сравнение РЦ

Пары «сеть × завод», сведённые из двух независимых сторон: отчёты приходят из
файла отчётов, размеры — из файла размеров. Соединение `FULL JOIN`: завод
бывает в одном файле и отсутствует в другом, и такой РЦ обязан остаться в
сравнении со своими цифрами, а не исчезнуть.

Колонки: число отчётов и из них через view; объём базы завода и число таблиц в
ней; сколько таблиц и мегабайт под отчётами и сколько без них; доля объёма под
отчётами; число схем; медиана глубины хранения; освобождаемый объём; суммарное
число запусков и суммарное время; «МБ на отчёт».

### 5.5.1. `v_report_duration` — время выполнения

Отчёты, отсортированные по суммарному времени. Поля: `avg_duration_sec`,
`total_duration_sec`, `duration_band` (меньше секунды / от 1 с / от 10 с /
минута и дольше). Это **вторая метрика стоимости**, независимая от объёма.

### 5.5.2. `v_catalog_overview` и `v_schema_overview`

`v_catalog_overview` группирует по **всем трём уровням** каталога и несёт
`reports_with_view`, `exclusive_pct_of_db`, `exec_count`, `total_duration_sec`.
`v_schema_overview` добавляет `percent_of_db`.

Агрегаты по папкам каталога (`folder_l1`) и по схемам БД: число отчётов, число
таблиц, суммарный объём.

### 5.6. Пять основных представлений в разрезе РЦ ⭐

Заказчик определил их как основные. **РЦ — это пара «сеть + завод»:** одно имя
завода встречается в разных торговых сетях и означает разные площадки, поэтому
все пять витрин несут обе колонки, а уникальность считается по паре.

| № | Витрина | Что сопоставляет | Связь |
| --- | --- | --- | --- |
| 1 | `v_tables_catalog` | Таблица + завод и её размер | один к одному |
| 2 | `v_rc_report_tables` | Отчёт и его таблицы | один ко многим |
| 3 | `v_rc_report_routines` | Отчёт и его функции/процедуры | один ко многим |
| 4 | `v_rc_report_usage` | Отчёт и обращения пользователей | один к одному |
| 5 | `v_rc_report_retention` | Отчёт и глубина хранения | один к одному |

Плюс `v_rc_summary` — шапка страницы: сколько в РЦ отчётов, таблиц, view,
материализованных view, временных объектов и процедур.

Правила, без которых цифры будут неверными:

- **№1 — это ровно файл размеров, ни больше ни меньше.** Сначала существует
  каталог таблиц, и только потом — отчёты, которые часть из них используют.
  В витрину попадает **каждая** строка файла размеров, включая таблицы, к
  которым не тянется ни один отчёт, и **не попадает ничего сверх неё**:
  объекты из отчётов без замера в список не подмешиваются, мост
  «отчёт ↔ таблица» только ссылается на этот список. Единица строки — пара
  «таблица + завод», потому что на каждом заводе размер свой. Колонка
  `report_count` в №1 **справочная**: она отвечает на вопрос «используется ли
  таблица», но не отбирает строки. Показатели, считающие таблицы (например,
  «не используются отчётами»), берут `COUNT(DISTINCT full_name)`: счёт по
  строкам завысил бы их во столько раз, на скольких заводах живёт таблица.
- **№2 включает только `TABLE`.** View, mat.view, временные и
  generated-объекты отфильтрованы: они не отражают физического хранения.
- **Суммировать объём по всем РЦ сразу нельзя** — одна таблица обслуживает
  отчёты нескольких РЦ. В интерфейсе показатели считают каждый объект один
  раз, а расхождение между числом строк и числом объектов выводится явно.
- **№4 меряет обращения, а не уникальных пользователей.** Заказчик подтвердил,
  что мерой активности служит «Кол-во обращений». Колонка `distinct_users`
  остаётся в модели и заполнится, если появится отдельный источник.
- **Глубина отчёта — максимум по его таблицам.** Отчёт показывает столько
  дней, сколько хранит самая «долгая» его таблица. Границы: до 30 / 31–45 /
  более 45 дней, плюс «Не задана».

### 5.7. `v_report_overlap` — пересечение отчётов

Пары отчётов с коэффициентом Жаккара по множествам **настоящих таблиц**
(`object_kind = 'TABLE'`) ≥ 0.8 — кандидаты на объединение. Ограничение:
только пары, где у обоих ≥ 2 таблицы.

**Сравниваются только отчёты одного РЦ.** Один и тот же отчёт заведён на
нескольких заводах — это нормальное устройство, а не дубль: объединять там
нечего, а межзаводских пар набегает столько, что за ними не видно настоящих
кандидатов. Сравнение идёт через `COALESCE`, а не напрямую: `NULL = NULL` в
SQL неверно, и отчёты без указанного завода выпали бы из сравнения совсем.
Ограничение по РЦ заодно делает ненужным отбор по совпадению имени и
каталога: внутри одного завода пара «имя + каталог» уникальна по ключу
отчёта.

Страница **«Похожие отчёты»** (раздел «Отчёты») не читает эту витрину
напрямую — у неё свой запрос с тем же принципом (только TABLE, только внутри
одного РЦ), но с порогом сходства, управляемым ползунком, и с разбором
конкретной пары по щелчку: какие таблицы общие, какие есть только у одного из
отчётов. Порог «не меньше 2 общих таблиц» обязателен и в этом запросе — без
него любые два отчёта, использующие общий справочник вроде календаря, попали
бы в кандидаты, а таких пар на реальных данных могут быть десятки тысяч.

## 7. ETL: требования к поведению

0. **Версия структуры.** При любом изменении `sql/01_schema.sql` или
   `sql/02_views.sql` обязательно поднять `SCHEMA_VERSION` в
   `src/reportsdb/config.py` и обновить слепок в
   `test_schema_version_matches_view_set`. Иначе у пользователей останется
   несовместимая база, а приложение не сможет об этом предупредить.
1. **Идемпотентность.** `build` всегда пересоздаёт `reports.duckdb` с нуля.
   Существующий файл переименовывается в `reports.duckdb.bak` (одна копия).
1.1. **Несколько файлов на роль.** Выгрузка приходит по файлу на завод, поэтому
   `build` принимает список файлов отчётов, а `table_sizes.files` и
   `report_usage.files` — списки. Файлы **склеиваются до разбора**, а не
   грузятся по очереди: сквозная нумерация `report_id` и `table_id` ведётся по
   всему набору, и загрузка по одному файлу выдавала бы одинаковые ключи для
   разных строк. Завод берётся из колонок ТС и Завод внутри файла, а не из
   того, какой это файл, — иначе размеры разных заводов молча сложились бы в
   один. Если файлов размеров несколько, а колонки завода в них нет,
   выставляется `stats.size_files_without_plant`: падения не будет, но цифры
   неверные, и промолчать об этом нельзя. Догрузка одного завода к собранной
   базе намеренно не поддержана — она порождает состояние «половина заводов
   свежая, половина старая», о котором по базе не догадаться.
2. **Разбор списка таблиц.** Разделитель `;` (настраивается). Пустые элементы
   отбрасываются. Элемент без точки → сначала попытка восстановить схему по
   файлу размеров (см. п. 2.1); если не вышло — `schema_name = '(unknown)'`,
   `schema_source = 'не определена'`, `is_parsed_ok = FALSE`. Элемент с двумя
   и более точками → берутся два последних сегмента (случай
   `db.schema.table`), остальное отбрасывается.
2.1. **Восстановление схемы по файлу размеров.** До загрузки отчётов по файлу
   размеров строится индекс «имя таблицы → схема» — только для имён, у
   которых в файле встречается ровно одна схема. Ссылка без схемы, чьё имя
   попало в индекс, получает эту схему и `schema_source = 'файл размеров'`;
   неоднозначные имена (несколько схем сразу) не восстанавливаются. Индекс
   строится один раз, до `_load_reports`, поэтому не зависит от того, в каком
   порядке отчёты и файл размеров загружаются в базу.
3. **Нормализация пути каталога.** Обратные слэши → прямые, схлопывание
   повторов, ведущий `/`, без завершающего `/`. Пустой путь → `/`.
4. **Отбраковка.** Строка без имени отчёта попадает в `etl_reject` и не
   прерывает загрузку. Строка без таблиц загружается — отчёт без источников
   валиден и интересен аналитике.
5. **Отчёт о загрузке.** В stdout: число строк прочитано / загружено /
   отброшено, число уникальных таблиц, число неразобранных элементов.
6. **Кодировка и типы.** Все текстовые поля читаются как строки — недопустимо,
   чтобы pandas превратил `1.2` в имя таблицы или потерял ведущие нули.

## 8. Streamlit-приложение (вариант A)

Меню собрано разделами через `st.navigation` — «Данные», «Аналитика РЦ»,
«Отчёты», «Справочники», «Инструменты». Каждое из пяти основных представлений
получило **отдельную страницу** внутри раздела «Аналитика РЦ»: вкладки внутри
одной страницы прятали содержимое и не давали ссылаться на конкретный разрез.

Два правила, общие для всех страниц:

- **Выбор РЦ живёт в `session_state`** и не сбрасывается при переходе между
  страницами раздела.
- **Поиск — одним полем сразу по нескольким колонкам**: заказчик должен
  находить строку и по наименованию таблицы, и по наименованию отчёта, не
  выбирая заранее, что именно ищет (`search_box` в `app/_shared.py`).

Страницы:

0. **Загрузка данных** — единственный путь записи в базу через интерфейс.
   Файлы берутся из `data/raw/` или перетаскиваются на страницу (сохраняются
   туда же). Пользователь указывает роль каждого файла и нажимает «Загрузить».
   Отдельная кнопка собирает HTML для коллег.

   Проверка колонок идёт **по каждому выбранному файлу** — отдельной вкладкой
   на файл. Для каждого ожидаемого поля показано, найдена ли колонка и что
   именно перестанет работать без неё; список потерь собирается в один блок.
   Блокирует загрузку только отсутствие имени отчёта; отсутствие `SIZE_MB` в
   файле размеров блокирует его использование. Отсутствие `SEGMENT_TYPE` даёт
   предупреждение: без него индексы попадут в размер таблиц и завысят его.

   Перед пересборкой приложение обязано закрыть соединения с БД
   (`release_db()`): под Windows занятый файл нельзя ни переименовать, ни
   перезаписать. После пересборки кэши сбрасываются, иначе страницы аналитики
   продолжат показывать прежние данные.

   **Очистка базы** — свёрнутый блок сразу под текущим состоянием, до всех
   `st.stop()` страницы: ниже кнопка просто не отрисовалась бы при пустой
   папке или невыбранном файле. Стирает все данные и оставляет **пустую базу
   нужной структуры**, а не удаляет файл: страницы аналитики продолжают
   открываться и показывают нули вместо ошибки «база не найдена», а версия
   структуры остаётся текущей. Резервная копия `.bak` удаляется вместе с
   базой — очистку просят, когда рабочих данных на машине быть не должно, и
   копия рядом сохранила бы ровно то, что просили стереть; флажок оставляет
   её при необходимости. Исходные файлы в `data/raw/` не трогаются, и
   страница прямо говорит, сколько их там осталось. Защита от случайного
   нажатия — свёрнутый блок и обязательный флажок подтверждения.

1. **Обзор** — главный дашборд, всё в разрезе выбранного РЦ, выбор в шапке,
   выбранная пара «сеть + завод» вынесена в подзаголовок. Сверху вниз:

   - **строка плиток**: отчётов, таблиц, объём таблиц (ГБ), схем БД. Таблицы и
     объём берутся из каталога №1, то есть из файла размеров, и считаются по
     таблицам, а не по строкам «таблица + завод»;
   - **три круговых разреза** по три доли: объём по использованию (несколько
     отчётов / один / не используются), глубина хранения, обращения к отчётам.
     Больше трёх долей нельзя — см. журнал решений;
   - **справочные таблицы**: отчёты по каталогам первого уровня (столбики
     одним цветом) и схемы БД **таблицей**. Схемы именно таблицей: их много,
     столбики уезжали далеко вниз, а у части схем размер неизвестен — на
     диаграмме это было пустое место. Схемы без размера в таблицу не
     попадают, их число указано подписью;
   - **качество исходных данных** (отбраковка, ссылки без схемы). РЦ не
     касается: это свойство загрузки, а не площадки.

   Высота таблиц считается по числу строк (`table_height()`) — фиксированная
   высота у короткой таблицы оставляет полосу пустых строк.

1.1. **№1 «Таблицы и размеры»** — единственная страница раздела «Аналитика РЦ»,
   которая **не** подчиняется выбору РЦ в шапке: это самостоятельный каталог
   таблиц из файла размеров и только из него. Строка — пара «таблица + завод».
   Свои фильтры: сеть, завод, связь с отчётами («все» / «используются
   отчётами» / «не используются»), поиск по имени. KPI: строк
   «таблица + завод», уникальных таблиц, суммарный объём, сколько таблиц не
   использует ни один отчёт. Под таблицей — подпись, сколько ссылок отчётов
   указывает на таблицы вне файла размеров: в список они не добавляются, но
   промолчать о них нельзя, у таких отчётов объём занижен.

1.5. **Карточка отчёта** — список отчётов строками-кнопками: щелчок в любом
   месте строки разворачивает полную картину, повторный щелчок её сворачивает.
   Видно, какие таблицы использует отчёт и сколько каждая весит, сколько раз он
   запускался, его view, временные объекты и процедуры, а также отчёты-соседи,
   которые используют те же таблицы. Сортировка — отдельным полем, полная
   таблица с сортировкой по колонкам и выгрузкой — в свёрнутом блоке.

1.6. **№2 «Отчёт → таблицы»** — два вида одной связи. «По отчётам»: строка —
   отчёт, видно из каких таблиц он состоит. «По таблицам»: строка — таблица,
   видно в какие отчёты она попадает. Щелчок по строке в любом из видов даёт
   разбор: показатели строки и её таблицы-источники (или отчёты-потребители).
   В виде «по таблицам» объём берётся как максимум по строкам таблицы, а не
   как сумма: одна таблица приходит там в нескольких отчётах.

2. **Объём и стоимость** ⭐ — построена вокруг вопроса «на какие таблицы
   ссылается отчёт и сколько они весят суммарно»: витрина
   `v_report_tables_summary` даёт и число таблиц, и их перечень, и сумму
   размеров одной строкой. Две вкладки по двум метрикам стоимости:
   «Объём данных» (топ-20 по `exclusive_mb`, скаттер «объём против частоты») и
   «Время выполнения» (топ-20 по суммарному времени, распределение по
   длительности выборки). Фильтры: сеть, завод, три уровня каталога, работа
   через view, покрытие размерами. Уровни 2 и 3 — каскадом от верхнего.
3. **Таблицы** — справочник **всех объектов-источников**, а не только таблиц:
   `v_table_criticality`, поиск, фильтр по типу объекта русскими названиями,
   флажок «только те, что не используются отчётами». Сверху — разбивка «каких
   объектов сколько» по типам: без неё не видно, что представления в данных
   вообще есть. В таблице есть колонка «Тип определён» — колонка файла / маска
   имени / файл размеров / по умолчанию.
4. **Кандидаты на вывод** — `v_decommission_candidates` с фильтром по
   `confidence`, выгрузка в CSV.
4.1. **Похожие отчёты** — пары отчётов с похожим или совпадающим набором
   таблиц (см. 5.7), порог сходства регулируется ползунком, щелчок по паре
   раскрывает список общих и различающихся таблиц.

4.2. **ABC-анализ** — отчёты, отсортированные по выбранной мере и разрезанные
   по накопленной доле: A до 80%, B до 95%, C — хвост. Плитки по группам,
   кривая накопления с опорными линиями 80/95%, круговая по долям групп,
   таблица с фильтром по группе. Диаграмму Парето рисовать нельзя: она кладёт
   столбцы и кривую на две разные оси.

   Мер четыре, и порядок неслучаен. Первая — «Объём таблиц отчёта, МБ»
   (`gross_mb`): сколько данных отчёт читает; есть почти у каждого и читается
   без оговорок. «Освободится при выводе, МБ» (`exclusive_mb`) вторая: она
   считается только по таблицам, которых не касается больше никто, и у отчёта
   на общих таблицах честно равна нулю — такой отчёт в анализ по этой мере не
   попадает вовсе. Дальше «Число обращений» и «Суммарное время выполнения».

   Под выбором меры выводится её определение, а под плитками — **сколько
   отчётов в анализ не вошли и почему**. Без этой строки главный вопрос
   читателя «почему список короче, чем отчётов в базе» остаётся без ответа.

5. **Сети и заводы** — сравнение РЦ между собой (см. 5.5). Плитки: сетей,
   заводов, объём базы, доля под отчётами. Ниже — стопка по каждому заводу
   «под отчётами / без отчётов» (две величины одной природы и одной шкалы —
   честные столбики, а не две оси) и таблица сравнения. Строки-заглушки
   «(не указана)/(не указан)» в счётчики сетей и заводов не идут: это не сеть
   и не завод, а незаполненная колонка.

5.1. **Файл для коллег** (раздел «Инструменты») — сборка самодостаточного
   HTML. Отдельная страница, а не блок внизу загрузчика: файл собирают не в
   тот же момент, когда грузят данные, а на странице загрузки он к тому же
   оказывался за `st.stop()` и просто не отрисовывался, пока файлы не выбраны.
   Показывает, что попадёт внутрь, дату и размер уже собранного файла и
   напоминает, что внутри рабочие данные. Кнопка скачивания живёт вне
   обработчика нажатия — иначе она исчезала бы при первом же перезапуске
   страницы, который сама и вызывает.

6. **SQL** — произвольный запрос к БД с ограничением 5000 строк и выгрузкой CSV.
   Сверху — справочник структуры: каждая таблица и витрина с назначением, под
   ней список полей с типами и пояснением к неочевидным. Колонки читаются из
   `information_schema`, а описания лежат словарём в коде, поэтому справочник
   не разъезжается со схемой. Там же — два правила, без которых запрос даст
   неверные цифры: соединять отчёт с размером только через
   `v_report_table_size` и не складывать `gross_mb` по отчётам.

Требования: работа полностью офлайн (без CDN), кириллица в подписях,
единая палитра, все таблицы выгружаются в CSV, единый вид интерфейса
(`inject_theme()` в `app/_shared.py`) — карточки-показатели, мягкие рамки
таблиц, приглушённые заголовки разделов меню, одинаково в светлой и тёмной
теме.

## 9. Самодостаточный HTML (вариант B)

Один файл `dist/reportsdb.html`. Внутри: данные как JSON, стили и скрипты
инлайном, ноль внешних запросов. Обязан открываться по `file://` в Chrome, Edge,
Firefox.

**Состав повторяет разделы приложения.** Коллега без Python и Docker обязан
видеть то же, что владелец базы: вкладки собраны по тем же группам меню, и в
каждой те же показатели, те же колонки и тот же разбор выбранной строки.

| Группа вкладок | Вкладки |
| --- | --- |
| Данные | Обзор: четыре плитки в разрезе РЦ, сравнение РЦ, схемы БД таблицей, топ-20 по освобождаемому объёму |
| Аналитика РЦ | №1 Таблицы и размеры · №2 Отчёт → таблицы · №3 Отчёт → функции · №4 Отчёт → обращения · №5 Глубина хранения |
| Отчёты | Карточка отчёта · Объём и стоимость · Кандидаты на вывод · Похожие отчёты · ABC-анализ |
| Справочники | Объекты-источники: таблицы, view, mat.view, временные, процедуры |

Общие свойства:

- **Выбор РЦ один на весь файл** — как в приложении. Плитки показателей
  считаются по тому, что реально показано, а не по всей базе.
- **№2 разделён на два вида**, «По отчётам» и «По таблицам», плюс полный
  список связей; щелчок по строке в любом из них разворачивает разбор.
- **Разбор строки** есть там же, где в приложении: карточка отчёта, оба вида
  №2, пара в «Похожих отчётах». Повторный щелчок снимает выбор.
- **Никаких `LIMIT`** в запросах выгрузки: обрезка молча показывала бы меньше,
  чем приложение. Единственный отбор — содержательный порог сходства в
  «Похожих отчётах».
- Сортировка, поиск, фильтры, выгрузка текущей выборки в CSV, светлая и тёмная
  тема. Целевой размер — до 5 МБ.

**Чего в файле нет:** загрузки данных, произвольного SQL и диаграмм Plotly —
это инструменты владельца базы, а не читателя. Диаграммы, которые остались,
нарисованы на чистом CSS.

## 11. Порядок работы агента при появлении реального Excel-файла

0. Убедиться, что `data/raw/` под `.gitignore` (см. 3.1.1). Файл заказчика
   никуда не выкладывается.
1. Положить файл в `data/raw/`.
2. `python -m reportsdb profile data/raw/<файл>` — вывести листы, заголовки,
   по 5 примеров значений, долю пустых.
3. Заполнить `config/mapping.yml` по факту. Ничего не угадывать: если смысл
   колонки неясен — спросить заказчика.
4. `python -m reportsdb build` — собрать БД. Проверить сводку и `etl_reject`.
5. Прогнать `tests/` — контрольные проверки целостности.
6. `python -m reportsdb export-html` — собрать HTML.
7. Обновить раздел 15 и запушить.

## 12. Контроль качества

Проверки в `tests/test_integrity.py`, запускаются на синтетических данных и на
реальных:

- у каждой связи в мосте существуют обе стороны (нет висячих ключей);
- `full_name` в `dim_table` уникален;
- сумма `exclusive_mb` по всем отчётам ≤ сумме `total_mb` по всем таблицам —
  ключевая защита от двойного учёта;
- число строк исходника = загружено + отброшено;
- все витрины выполняются на пустых фактах и возвращают результат без ошибок;
- **каждое загруженное поле присутствует хотя бы в одной витрине** — иначе
  колонку прочитали впустую (`test_every_loaded_field_is_visible_in_analytics`);
- `total_duration_sec` равен `exec_count × avg_duration_sec`;
- `SCHEMA_VERSION` записана в базу, а слепок SQL сверяется с ней: правка схемы
  без поднятия версии роняет тест;
- таблица №1 содержит **ровно** строки файла размеров: ни потерь, ни добавок
  из отчётов, и ни одна пара «таблица + завод» не показана дважды; №2 содержит
  только `TABLE`, №3 только `ROUTINE`, границы глубины 30/45 расставлены верно;
- одна таблица имеет разный размер на разных заводах, а резолвер
  `v_report_table_size` не размножает строки отчёта: число его строк равно
  числу строк `bridge_report_table`, и для отчёта берётся замер его завода;
- фактические заголовки заказчика (`№`, `Наименование отчета`, `Каталог`,
  `Таблицы источники данных`) сопоставляются без правок конфига;
- `.gitignore` закрывает `data/raw/*`, `data/*.duckdb` и `dist/`;
- схема, восстановленная по единственному совпадению имени в файле размеров,
  даёт ровно одну строку `dim_table` (не дублирует запись из файла размеров);
  неоднозначное имя (несколько схем сразу) не восстанавливается и остаётся
  `(unknown)`; `is_parsed_ok` всегда согласован со `schema_source`.

## 13. Ограничения и риски

| Риск | Смягчение |
| --- | --- |
| Список таблиц в Excel неполон или устарел (заполнялся руками) | В UI явная оговорка: анализ отражает содержимое файла, а не фактические зависимости. Достоверный источник — парсинг `.rdl` или `ReportServer.ExecutionLog`. |
| Двойной учёт общих таблиц | Введён `exclusive_mb`; `gross_mb` помечен как небезопасный для суммирования. |
| Неполные данные о размерах | `size_coverage_pct` и понижение `confidence`. |
| Отчёт может тянуть данные через хранимые процедуры и вьюхи | Фиксируется как известное ограничение; при появлении данных добавить `object_type` в `dim_table`. |
