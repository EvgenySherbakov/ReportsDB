# Архитектура решения

Краткое описание компонентов: что из чего состоит, кто за что отвечает и как
данные проходят через систему.

Подробности решений и обоснования — в [ТЗ](TZ.md). Инструкции по запуску — в
[RUNBOOK](RUNBOOK.md).

---

## Общая картина

```
   Excel-файлы                ЯДРО                    ИНТЕРФЕЙСЫ
   (локально)

  ┌───────────┐        ┌──────────────┐         ┌────────────────────┐
  │ Отчёты    │        │              │         │ Streamlit          │
  │ + каталог ├───────▶│              │────────▶│ 5 страниц,         │
  │ + таблицы │        │     ETL      │         │ localhost:8501     │
  └───────────┘        │   (Python)   │         └────────────────────┘
  ┌───────────┐        │              │  reports
  │ Размеры   ├───────▶│  нормализа-  │──.duckdb┌────────────────────┐
  │ таблиц    │        │  ция, разбор │────────▶│ HTML-файл          │
  └───────────┘        │  связей      │         │ данные внутри,     │
  ┌───────────┐        │              │         │ открыть двойным    │
  │ Частота   ├───────▶│              │         │ кликом             │
  │ запусков  │        └──────┬───────┘         └────────────────────┘
  └───────────┘               │
                              ▼
                     ┌──────────────────┐
                     │ mapping.yml      │  имена колонок — только здесь
                     │ sql/*.sql        │  схема и витрины
                     └──────────────────┘
```

Всё выполняется на одной машине. Сервера, сети и внешних сервисов нет.

## Компоненты

### 1. Хранилище — DuckDB

**Что это:** встраиваемая аналитическая СУБД. Вся база — один файл
`data/reports.duckdb`.

**Зачем такая:** не требует установки и администрирования, файл копируется как
обычный документ, колоночный движок быстро считает агрегаты по размерам и
связям. SQL близок к PostgreSQL.

**Модель данных** — «звезда» с мостом для связи многие-ко-многим:

| Объект | Содержит |
| --- | --- |
| `dim_report` | Отчёты: номер, наименование, торговая сеть, завод, уровни каталога, признак работы через view |
| `dim_table` | Объекты-источники: таблицы, view, mat.view, временные, процедуры — различает `object_kind` |
| `bridge_report_table` | Связи «отчёт ↔ таблица», развёрнутые из ячейки со списком |
| `fact_table_size` | Размеры таблиц в разрезе «таблица + ТС + завод»: МБ, доля в объёме БД, число сегментов, глубина хранения |
| `fact_report_usage` | Использование: запусков и средняя длительность в секундах |
| `etl_run`, `etl_reject` | Журнал загрузок и отбракованные строки |

Обе таблицы фактов создаются всегда. Пока данных нет — пусты, витрины при этом
работают.

### 2. Загрузчик — ETL

`src/reportsdb/` — чтение Excel/CSV, нормализация, запись в базу.

| Модуль | Отвечает за |
| --- | --- |
| `config.py` | Пути проекта, чтение `mapping.yml`, сопоставление заголовков |
| `excel.py` | Чтение листа как текста, без догадок о типах |
| `normalize.py` | Разбор `схема.таблица`, нормализация путей каталога, чисел |
| `etl.py` | Полная пересборка базы, журнал, отбраковка |
| `profile_source.py` | Показ структуры файла до загрузки |
| `export_html.py` | Сборка автономного HTML |
| `sample_data.py` | Синтетические данные для проверки без реальных файлов |
| `cli.py` | Команды `profile`, `build`, `export-html`, `sample` |

**Ключевые свойства:**

- **Идемпотентность.** Каждая загрузка пересобирает базу с нуля; прежняя версия
  сохраняется как `reports.duckdb.bak`. Дублей и накоплений не возникает.
- **Ничего не теряется молча.** Строки, которые не удалось разобрать, попадают
  в `etl_reject` с причиной, а не исчезают.
- **Терпимость к «грязи».** Разбираются `[dbo].[Orders]`, лишние пробелы,
  имена вида `db.schema.table`, имена без схемы, дубликаты внутри ячейки,
  признаки «да/нет» в разном написании.
- **Агрегация сегментов.** Файл размеров приходит построчно по сегментам БД:
  секции одной таблицы суммируются, индексные и LOB-сегменты пропускаются.

### 3. Конфигурация сопоставления — `config/mapping.yml`

**Единственное** место, где записаны имена колонок Excel. В коде ETL их нет.

Для каждого поля модели задан список синонимов; сопоставление игнорирует
регистр, краевые пробелы и различие «ё»/«е». Чтобы поддержать новый формат
файла, достаточно дописать строку в этот YAML — код не меняется.

`config/mapping.sample.yml` — то же самое для демонстрационных данных.

### 4. Витрины — `sql/`

| Файл | Содержит |
| --- | --- |
| `01_schema.sql` | DDL таблиц |
| `02_views.sql` | Аналитические представления |

Вся аналитика — SQL-представления поверх модели, а не код в приложении. Их
видно из любого SQL-клиента и можно использовать без Streamlit.

| Представление | Отвечает на вопрос |
| --- | --- |
| `v_report_footprint` | Сколько данных за каждым отчётом |
| `v_table_criticality` | Какая таблица в скольких отчётах используется |
| `v_report_cost_value` | Объём и время против частоты использования, квадранты |
| `v_network_overview` | Разрез по торговым сетям и заводам |
| `v_report_duration` | Время выполнения как отдельная метрика стоимости |
| `v_decommission_candidates` | Что можно выводить и сколько это освободит |
| `v_catalog_overview`, `v_schema_overview` | Сводка по папкам и схемам |
| `v_report_overlap` | Отчёты с почти совпадающим набором источников (только `TABLE`; страница «Похожие отчёты» использует свой запрос с тем же принципом и порогом-ползунком) |
| `v_tables_catalog`, `v_rc_report_tables`, `v_rc_report_routines`, `v_rc_report_usage`, `v_rc_report_retention` | Пять основных представлений в разрезе РЦ. №1 — ровно содержимое файла размеров: список таблиц БД берётся только оттуда |
| `v_report_table_size` | Размер таблицы для конкретного отчёта: берёт замер завода этого отчёта. Через неё соединяются отчёты и размеры |
| `v_report_tables_summary` | Отчёт, его таблицы одной строкой и их суммарный размер |

**Главная особенность модели расчёта.** Общие таблицы принадлежат нескольким
отчётам, поэтому в витринах два разных показателя объёма:

- `gross_mb` — сумма всех таблиц отчёта; **по отчётам не суммируется**, при
  сложении многократно учитывает общие таблицы;
- `exclusive_mb` — только таблицы, которых не касается ни один другой отчёт;
  это и есть объём, который реально освободится при выводе отчёта.

Плюс `size_coverage_pct` — доля таблиц отчёта с известным размером, защита от
выводов по неполным данным. Инвариант «сумма `exclusive_mb` не превышает
реальный объём хранилища» закреплён тестом.

### 5. Интерфейс А — Streamlit

`app/` — веб-приложение на локальном порту 8501.

`app/Home.py` — точка входа: собирает меню через `st.navigation`. Разделы
вложенные, поэтому папка `pages/` не годится — страницы лежат в `app/views/`.

| Раздел | Страница | Назначение |
| --- | --- | --- |
| Данные | `overview.py` | Обзор: показатели, каталог, схемы, качество данных |
| Данные | `load.py` | Загрузка файлов, проверка колонок, пересборка базы, сборка HTML |
| Аналитика РЦ | `rc1_tables.py` | №1 Объект и его размер, один к одному |
| Аналитика РЦ | `rc2_report_tables.py` | №2 Отчёт и его таблицы, один ко многим |
| Аналитика РЦ | `rc3_routines.py` | №3 Отчёт и его функции и процедуры |
| Аналитика РЦ | `rc4_usage.py` | №4 Отчёт и обращения пользователей |
| Аналитика РЦ | `rc5_retention.py` | №5 Отчёт и глубина хранения |
| Отчёты | `report_card.py` | Карточка отчёта: клик по строке → таблицы, размеры, статистика |
| Отчёты | `cost.py` | На какие таблицы ссылается отчёт и сколько они весят |
| Отчёты | `candidates.py` | Список на вывод с уровнем уверенности |
| Справочники | `tables.py` | Критичность таблиц и зависимости |
| Справочники | `networks.py` | Организационный разрез, доля отчётов через view |
| Инструменты | `export.py` | Сборка самодостаточного HTML-файла для коллег |
| Инструменты | `sql.py` | Произвольный запрос к базе |

Выбор РЦ общий для всех страниц: он хранится в `session_state`, поэтому при
переходе между страницами не сбрасывается. Поиск во всех таблицах — одним
полем сразу по имени таблицы и имени отчёта.

`app/_shared.py` — общее: подключение к базе, палитра, русские подписи колонок,
выгрузка CSV, освобождение файла базы перед пересборкой, безопасный показ
пустых значений (`num`, `is_blank`) и выбор строки щелчком (`row_picker`).

`row_picker` существует потому, что `st.dataframe` выделяет строку только
флажком в левой колонке — щелчок по самой строке виджет не замечает. Поэтому
строка там, где по ней нужно щёлкать, — кнопка во всю ширину.

База открывается **только на чтение**: изменить данные из интерфейса нельзя,
единственный путь записи — загрузчик.

### 6. Интерфейс Б — автономный HTML

`src/reportsdb/templates/standalone.html` + `export_html.py` → один файл
`dist/reportsdb.html` (~100 КБ).

Данные встроены как JSON, агрегация — на JavaScript, стили и скрипты внутри.
Ни одного внешнего запроса: открывается по `file://` двойным кликом, работает
без интернета. Светлая и тёмная тема, сортировка, поиск, фильтры, выгрузка CSV.

Реализовано без DuckDB-WASM намеренно — обоснование в разделе 2.1 ТЗ.

### 7. Упаковка и запуск

| Компонент | Назначение |
| --- | --- |
| `docker/Dockerfile`, `docker-compose.yml` | Запуск одной командой без Python на машине |
| `scripts/run.sh`, `run.bat` | Запуск на Python: окружение, зависимости, приложение |
| `scripts/rdb.sh`, `rdb.bat` | Команды `reportsdb` тем же Python, что и приложение: из обычной консоли пакет не виден, он стоит в окружении проекта |
| `pyproject.toml` | Зависимости и команда `reportsdb` |
| `tests/test_integrity.py` | Проверки целостности модели и корректности расчётов |

## Поток данных при загрузке

1. Файлы попадают в `data/raw/` — вручную или перетаскиванием в интерфейс.
2. Заголовки листа сопоставляются с полями модели по `mapping.yml`; результат
   показывается до загрузки, чтобы ошибка обнаружилась заранее.
3. Приложение отпускает файл базы (иначе под Windows его не заменить).
4. ETL пересоздаёт базу: DDL → отчёты и таблицы → факты → представления →
   запись в журнал.
5. Кэши интерфейса сбрасываются, страницы аналитики показывают новые данные.

Шаги 3–5 выполняются по нажатию **Загрузить**; та же логика доступна командой
`scripts\rdb.bat build`.

## Границы решения

**Что система делает:** превращает выгрузку в базу со связями и считает
аналитику по объёму и востребованности отчётов.

**Чего не делает:** не подключается к SSRS, не читает `.rdl`, не следит за
изменениями, не хранит историю — каждая загрузка заменяет предыдущую.

**Главное ограничение достоверности:** источником связей служит содержимое
Excel-файла. Обращения к данным через хранимые процедуры и view в нём не
видны, поэтому список источников может быть неполным. Для отчётов с признаком
«Используется view» это известно точно — они помечены и не могут получить
высокую уверенность в кандидатах на вывод. Достоверные источники
— разбор `.rdl` или журнал `ReportServer.ExecutionLog`; переход на них не
потребует менять модель данных.

**Данные не покидают машину.** Папки `data/` и `dist/` закрыты `.gitignore`, в
репозиторий попадает только код. Docker-образ содержит собранную базу и
предназначен для передачи внутри команды.
