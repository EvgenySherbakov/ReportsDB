# ReportsDB — локальная база отчётности SSRS

**Русский** · [English](README.en.md)

Excel-выгрузка по отчётам SSRS превращается в локальную аналитическую базу
(**DuckDB**, один файл) с готовыми витринами и двумя способами смотреть данные:

| Вариант | Кому | Как запускается |
| --- | --- | --- |
| **Streamlit-приложение** | у кого есть Docker или Python | `docker compose up` → браузер |
| **Один HTML-файл** | у кого только браузер | двойной клик по файлу |

Главный вопрос, на который отвечает база: **сколько данных обслуживает каждый
отчёт и что реально освободится, если его вывести из эксплуатации.**

## Быстрый старт

### Посмотреть на демо-данных (ничего своего не нужно)

Одной командой: `scripts\run.bat` (Windows), `./scripts/run.sh` (Linux/macOS) —
демо-данные сгенерируются сами, если базы ещё нет.

По шагам то же самое:

```bash
scripts/rdb.sh sample                                   # синтетический Excel
scripts/rdb.sh build --config config/mapping.sample.yml \
    data/raw/sample_reports.xlsx                        # собрать БД
scripts/run.sh                                          # открыть аналитику
```

### Загрузить свои данные

Файлы остаются **только на вашей машине**: `data/raw/`, `data/*.duckdb` и
`dist/` закрыты `.gitignore`, в репозиторий уходит один код.

Маппинг настроен под фактические заголовки — конфиг править не нужно:

- **файл отчётов:** `№`, `ТС`, `Завод`, `Каталог 1/2/3-го уровня`,
  `Наименование отчета`, `Используется view`, `Таблицы источники данных`, а
  также — если появятся — `View`, `Mat.view`, `Временные таблицы`,
  `Функции/процедуры`. `Ср. дл. (сек)` и `Кол-во обращений` из этого файла **не
  читаются**, даже если физически есть в колонках, — статистика приходит
  только отдельным файлом, см. ниже;
- **файл размеров** (выгрузка сегментов БД): `OWNER`, `SEGMENT_NAME`,
  `SEGMENT_TYPE`, `SIZE_MB`, `PERCENT_OF_TOTAL`, `Глубина хранения`;
- **файл статистики** (обязателен, если нужны обращения и длительность):
  `Наименование отчета`, `ТС`, `Завод`, `Кол-во обращений`, `Ср. дл. (сек)`;
- **файл SQL-запросов** (необязательно): `№`, `ТС`, `Завод`,
  `Каталог 1/2/3-го уровня`, `Наименование отчета`, `Запрос к базе данных` —
  показывается в «Инструменты → Запросы к БД из SSRS» и в карточке отчёта.

Тип объекта берётся из колонки, в которой объект перечислен. Если отдельных
колонок по типам нет, работает маска имени из `config/mapping.yml` — по
умолчанию включена одна: префикс `v_` (и `vw_`) означает представление.

Маска — последняя догадка. Объект, найденный в файле размеров, остаётся
таблицей в любом случае: у него есть сегменты, значит он физически хранится, как
бы он ни назывался. В справочнике «Таблицы» видно, откуда взят тип каждого
объекта — колонка «Тип определён».

**Через интерфейс — командная строка не нужна.** Страница **Загрузка данных**
в меню слева: положить файлы в `data/raw/` или перетащить их на страницу,
выбрать, что чем является, проверить сопоставление колонок и нажать
**Загрузить**. Пошагово — в [RUNBOOK](docs/RUNBOOK.md#как-загружать-данные).

**Через командную строку.** Запускайте через `scripts\rdb.bat` (Windows) или
`scripts/rdb.sh` (macOS/Linux): приложение живёт в виртуальном окружении
проекта, и `python -m reportsdb` из обычной консоли его не видит — падает с
«No module named reportsdb».

```bat
scripts\rdb.bat profile data\raw\reports.xlsx   :: что в файле
scripts\rdb.bat build   data\raw\reports.xlsx   :: собрать базу
scripts\rdb.bat diagnose                        :: сверить размеры с базой
scripts\rdb.bat clear                           :: стереть все данные
scripts\run.bat                                 :: смотреть
```

```bash
scripts/rdb.sh profile data/raw/reports.xlsx    # что в файле
scripts/rdb.sh build   data/raw/reports.xlsx    # собрать базу
scripts/rdb.sh diagnose                         # сверить размеры с базой
scripts/rdb.sh clear                            # стереть все данные
scripts/run.sh                                  # смотреть
```

`diagnose` нужен, когда числа в таблице №1 расходятся с исходным файлом: он
показывает, какие колонки распознаны, сколько строк какого типа сегмента учтено
и совпадает ли итог с базой. Имена таблиц не печатает — только числа.

`clear` стирает все загруженные данные и оставляет пустую базу нужной
структуры — аналитика продолжает открываться и показывает нули. Вместе с базой
удаляется и `reports.duckdb.bak`: очистку просят, когда рабочих данных на
машине быть не должно, и копия рядом сохранила бы ровно то, что просили
стереть (`--keep-backup`, если копия нужна). То же самое есть в интерфейсе:
**Загрузка данных → Очистить базу**. Исходные файлы в `data/raw/` не трогаются.

Имена колонок нигде в коде не зашиты — только в `config/mapping.yml`.

## Передача коллегам

**Через Docker** — им нужен только Docker:

```bash
docker compose -f docker/docker-compose.yml up --build
# http://localhost:8501
```

Образ включает содержимое `data/` — то есть собранную базу и исходные файлы.
Это сделано намеренно, чтобы коллеге хватило одной команды, но означает, что
образ содержит рабочие данные: не публикуйте его в открытых реестрах.

**Если у коллеги нет доступа к репозиторию**, передайте сам образ файлом:

```bat
docker compose -f docker\docker-compose.yml build
docker save reportsdb:latest -o reportsdb-image.tar
```

Коллега: `docker load -i reportsdb-image.tar`, затем
`docker run -d -p 8501:8501 --name reportsdb reportsdb:latest`. Файл выходит
около 1 ГБ; пошагово, вместе с обновлением и подключением своей папки, —
в [RUNBOOK](docs/RUNBOOK.md#передать-образ-коллеге).

**Через HTML** — им не нужно ничего:

```bash
scripts/rdb.sh export-html      # → dist/reportsdb.html
```

Либо в приложении: **Инструменты → Файл для коллег** → «Собрать HTML-файл».

Файл самодостаточен: данные, стили и скрипты внутри, ни одного внешнего запроса.
Открывается двойным кликом, работает офлайн, поддерживает светлую и тёмную тему,
поиск, сортировку и выгрузку в CSV.

**Внутри — все разделы приложения.** Меню слева повторяет меню приложения:
Обзор, вся «Аналитика РЦ» (№1–№5), весь раздел «Отчёты» (карточка, объём и
стоимость, кандидаты на вывод, похожие отчёты, уникальные отчёты, ABC-анализ),
справочники (объекты-источники, сети и заводы) и «Запросы к БД из SSRS» с текстом SQL по
каждому отчёту. Те же показатели, те же колонки, тот же разбор строки по щелчку,
общий выбор РЦ на весь файл. Ничего не обрезается: списки идут целиком, порог
сходства на «Уникальных отчётах» так же двигается ползунком. Совпадение состава
с приложением закреплено тестом — новая страница не появится в приложении молча,
не появившись в файле.

Не переносятся только загрузка данных и произвольный SQL — это инструменты
владельца базы, а не читателя.

## Что показывает аналитика

### Пять основных представлений в разрезе РЦ

РЦ — это пара «сеть + завод». Раздел меню **«Аналитика РЦ»**, по странице на
каждое представление:

| № | Витрина | Что сопоставляет |
| --- | --- | --- |
| 1 | `v_tables_catalog` | Каталог таблиц и размеров: пара «таблица + завод», один к одному. Ровно то, что есть в файле размеров — включая таблицы, которых нет ни в одном отчёте, и **только** их |
| 2 | `v_rc_report_tables` | Отчёт и его таблицы — только `TABLE`, без view и временных |
| 3 | `v_rc_report_routines` | Отчёт и его функции/процедуры |
| 4 | `v_rc_report_usage` | Отчёт и обращения пользователей |
| 5 | `v_rc_report_retention` | Отчёт и глубина хранения: до 30 / 31–45 / более 45 дней |

### Остальная аналитика

| Витрина | Отвечает на вопрос |
| --- | --- |
| `v_report_footprint` | Сколько данных за каждым отчётом |
| `v_table_criticality` | Какой объект в скольких отчётах — что сломается при его изменении |
| `v_report_cost_value` | Объём против частоты использования |
| `v_report_duration` | Время выполнения: средняя длительность и суммарные затраты |
| `v_decommission_candidates` | Что можно выводить из эксплуатации и сколько это освободит |
| `v_network_overview` | Сравнение РЦ: объём базы завода, сколько из него под отчётами, сколько без них |
| `v_catalog_overview`, `v_schema_overview` | Распределение по папкам каталога и схемам |
| `v_report_overlap` | Отчёты одного завода с почти одинаковым набором источников |
| `v_report_twin` | Двойники отчёта: в других ТС и на других заводах своей ТС (колонка `scope`) |
| `v_network_report_twin` | Отчёт сети целиком: заводы схлопнуты, видно, есть ли он в других ТС |
| `v_report_tables_summary` | Отчёт, перечень его таблиц и их суммарный размер |

### Карточка отчёта

Страница **«Карточка отчёта»**: щелчок по строке в таблице отчётов
разворачивает полную картину — какие таблицы использует отчёт и сколько каждая
весит, сколько раз он запускался, его view и процедуры, текст SQL-запроса (если
загружен отдельным файлом), а также отчёты-соседи по тем же таблицам.

### Похожие отчёты

Страница **«Похожие отчёты»** (раздел «Отчёты») ищет пары, ссылающиеся на один
и тот же набор настоящих таблиц — кандидаты на объединение. Порог сходства
(индекс Жаккара) регулируется ползунком, щелчок по паре показывает, какие
таблицы общие, а какие есть только у одного из отчётов.

**Сравниваются только отчёты одного завода.** Один и тот же отчёт заведён на
нескольких заводах — это нормальное устройство, а не дубль: объединять там
нечего, а межзаводских пар набегает столько, что за ними не видно настоящих
кандидатов.

### Уникальные отчёты

Страница **«Уникальные отчёты»** (раздел «Отчёты») отвечает на обратный вопрос:
**что есть своего**. Уникален отчёт, у которого на другой стороне нет ни тёзки,
ни близкого по набору таблиц двойника.

**Область сравнения выбирается переключателем**, потому что вопросов два:

- **Между ТС** — чего нет в других сетях. Сети пересекаются по отчётам заметно
  (у заказчика примерно на 70%), и различия между ними — главное, что нужно
  видеть. Единица счёта здесь — отчёт сети: стоящий на нескольких её заводах
  считается один раз.
- **Между заводами одной ТС** — чего нет у соседей. Единица счёта — запись
  отчёта на заводе.

Сверху — свод: отчётов всего, из них уникальных, доля, объём их таблиц и число
запусков. Щелчок по отчёту показывает его таблицы с размером и глубиной
хранения, запуски, среднюю длительность и то, **почему** он попал в уникальные:
ближайший отчёт другой стороны назван вместе с величиной сходства.

Порог сходства — ползунок: «тот же отчёт» на разных площадках успевает
разойтись по набору таблиц, и где кончается «тот же», решает читатель. Если
сравнивать не с чем (в базе одна сеть или в ТС один завод), страница говорит об
этом прямо: «все отчёты уникальны» там означает отсутствие данных, а не вывод.

### ABC-анализ

Страница **«ABC-анализ»** сортирует отчёты по выбранной мере и режет по
накопленной доле: **A** — первые отчёты, дающие 80% итога, **B** — следующие до
95%, **C** — длинный хвост. Отвечает на вопрос «с чего начинать»: обычно 20–30%
отчётов дают 80% нагрузки, и работа с группой A окупается, а группа C — готовый
список кандидатов на вывод.

Мер четыре, и они отвечают на разные вопросы:

| Мера | Что показывает |
| --- | --- |
| **Объём таблиц отчёта, МБ** | Сколько данных читает отчёт. Общая таблица считается у каждого отчёта, который её читает: для сравнения отчётов между собой так и надо, но сумма столбца больше объёма базы и объёмом базы не является |
| **Освободится при выводе, МБ** | Сколько места освободится, если отчёт вывести: только его собственные таблицы. У отчёта на общих таблицах это честный ноль |
| **Число обращений** | Сколько раз отчёт запускали |
| **Суммарное время выполнения** | Обращения × средняя длительность |

Отчёт с нулевой мерой в анализ не входит — страница прямо пишет, сколько таких
отчётов и почему.

### Запросы к БД из SSRS

Страница **«Запросы к БД из SSRS»** (раздел «Инструменты») показывает текст SQL, которым
формируется отчёт — из отдельного файла SQL-запросов. Здесь обратный порядок по
сравнению с карточкой отчёта: **поиск идёт и по тексту запроса**, поэтому вопрос
«какие отчёты трогают эту таблицу» решается прямо здесь — включая таблицы,
которые не попали в колонку «Таблицы источники данных» исходного файла.

Щелчок по отчёту показывает запрос с подсветкой синтаксиса, выгрузку в `.sql` и
рядом — **заявленные источники отчёта** с отметкой «есть в запросе». Расхождение
между списком источников из файла и текстом запроса видно сразу: если в запросе
есть таблица, которой нет в списке, объём отчёта занижен. Отметка «нет» бывает и
законной — объект может приходить через view или процедуру.

### Про `gross_mb` и `exclusive_mb` — важно

Общие таблицы попадают в несколько отчётов сразу:

- **`gross_mb`** — сумма размеров всех таблиц отчёта. **Складывать по отчётам
  нельзя**: на демо-данных сумма `gross_mb` завышает реальный объём вдвое.
- **`exclusive_mb`** — только таблицы, которых не касается ни один другой отчёт.
  Это и есть объём, который освободится при выводе отчёта. Складывается честно.
- **`size_coverage_pct`** — доля таблиц отчёта с известным размером; защищает от
  выводов по неполным данным.
- **`exclusive_pct_of_db`** — какую долю всей базы занимают эксклюзивные
  таблицы отчёта.

Стоимость меряется двумя независимыми величинами: **объёмом данных** и
**временем** (`total_duration_sec` = запусков × средняя длительность). Отчёт
бывает дешёвым по данным и дорогим по времени — это разные поводы для действий.

### Про размеры таблиц

Файл размеров — выгрузка сегментов БД, строка на сегмент. Сегменты одной
таблицы (секции) **суммируются**; индексные и LOB-сегменты пропускаются —
привязать их к таблице по этой выгрузке нельзя, поэтому размер индексов в
объём таблицы не входит.

### Про отчёты через view

Если отчёт обращается к данным через view, список таблиц-источников заведомо
неполон: за view стоят таблицы, которых в списке нет. Такой отчёт никогда не
получает высокую уверенность в кандидатах на вывод.

## Модель данных

```
        dim_report ──< bridge_report_table >── dim_table
             │                                     │
      fact_report_usage                     fact_table_size
```

Список таблиц из одной Excel-ячейки (`dbo.Orders;dbo.Customers`) разворачивается
в связь многие-ко-многим. Разбор терпит `[dbo].[Orders]`, лишние пробелы,
трёхсегментные имена `db.schema.table` и имена без схемы.

Если схема не указана, но имя таблицы встречается в файле размеров ровно с
одной схемой — она подставляется автоматически (файл размеров перечисляет все
таблицы БД независимо от отчётов). Неоднозначные имена не трогаются. Видно в
справочнике «Таблицы» столбцом «Схема определена».

`fact_table_size` и `fact_report_usage` создаются всегда. Пока соответствующие
файлы не загружены, они пусты — витрины при этом работают, а приложение честно
предупреждает, каких данных не хватает.

## Проверки

```bash
pytest -q
```

135 тестов: разбор имён таблиц, путей и признаков «да/нет», сопоставление
фактических заголовков обоих файлов, сборка пути из уровней каталога,
суммирование сегментов и отсев индексных, единицы длительности, отсутствие
висячих ключей, работа всех витрин на пустых фактах, самодостаточность HTML,
проверка что `exclusive_mb` не превышает реальный объём хранилища, и страж,
который следит, что каждое загруженное поле дошло до аналитики.

## После обновления кода

Если после `git pull` приложение пишет «База собрана прежней версией
программы» — откройте **Загрузка данных** и нажмите **Загрузить**. Структура
базы версионируется, и приложение само распознаёт несовместимость вместо того,
чтобы падать с ошибкой SQL.

## Ограничения

Анализ отражает содержимое Excel-выгрузки, а не фактические зависимости
отчётов. Обращения через хранимые процедуры и представления в списке источников
не видны. Достоверный источник — разбор `.rdl` или журнал
`ReportServer.ExecutionLog`; см. раздел 13 ТЗ.
